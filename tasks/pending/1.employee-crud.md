# Task: Implement Employee Management CRUD with Automatic Employee Role Assignment

## Objective

Implement complete Employee Management CRUD functionality in the existing Laravel application.

**Mandatory:** Follow the existing boilerplate, folder structure, architecture, coding patterns, UI components, authentication system, validation conventions, and reusable functionality. Do not introduce a new architecture or coding style.

## 1. Inspect the Existing Project First

Before making any changes:

1. Inspect the complete relevant project structure and read all applicable `.mdc` instructions.
2. Identify the existing user model, authentication mechanism, roles and permissions implementation, database schema, migrations, controllers, services, repositories, Form Requests, routes, frontend components, layouts, and tests.
3. Identify an existing CRUD module and follow its implementation pattern.
4. Determine whether the project uses Spatie Laravel Permission, a custom role system, or another existing role-management implementation.
5. Check installed package versions and existing role-related database tables before implementing role assignment.
6. Check Git status and preserve all existing uncommitted changes.

Do not assume a class, package, table, component, route, or relationship exists without verifying it.

## 2. Employee Management CRUD

Implement the complete functionality using the existing project's conventions.

### Create Employee

- Provide an employee creation form using the existing UI and form patterns.
- Include fields appropriate to the existing application, such as name, email, phone, employee code, department, designation, joining date, and status, where applicable.
- Inspect the existing user and employee schemas before deciding which fields belong to the users table or an employee-specific table.
- Reuse the existing user model and authentication system wherever appropriate.
- Validate required fields, email format, uniqueness, optional fields, and other applicable business rules.
- Hash passwords using the application's existing Laravel authentication facilities if employee account creation requires a password.
- Never store plaintext passwords or expose credentials in responses or logs.

### Mandatory Employee Role Assignment

Whenever an employee is created, the application must automatically assign the `employee` role.

Implement this exact business rule:

1. Check whether the `employee` role already exists using the existing role-management implementation.
2. If the role exists, reuse it.
3. If the role does not exist, create it using the existing role model, permissions package, database schema, and naming conventions.
4. Assign the `employee` role to the newly created employee account.
5. Complete employee creation and role assignment reliably, using a database transaction where appropriate.
6. Ensure role assignment occurs on every applicable employee-creation path, not just in the frontend.
7. Prevent duplicate role records by using the appropriate unique constraints and safe lookup-or-create behavior.
8. Handle concurrent requests safely where supported by the existing database schema.
9. Do not create duplicate employee roles on repeated employee creation requests.
10. Do not remove, rename, or modify existing roles or permissions unnecessarily.

If the application uses Spatie Laravel Permission, inspect its installed version and follow its existing configuration, guards, models, and role-assignment APIs. Use the correct guard for the employee account.

If the project uses a custom role implementation, extend that implementation instead of introducing Spatie or another package.

**Important:** Creating a role record is not sufficient. Verify that the newly created employee account is actually associated with the `employee` role and that the application's authorization system recognizes the assignment.

### Employee Listing

Implement an employee listing page using the existing table or DataTables implementation.

Support the features already established by the project, where applicable:

- Employee details.
- Search and filtering.
- Pagination.
- Sorting.
- View, edit, and delete actions.
- Existing status indicators and action controls.

Reuse installed packages and existing table components. Do not introduce a new table library unnecessarily.

### View Employee

- Display employee details using the existing detail-page, modal, or component conventions.
- Follow existing authorization rules.
- Do not expose passwords, password hashes, secrets, or sensitive internal fields.

### Edit Employee

- Allow authorized users to update permitted employee details.
- Preserve existing validation and unique-field rules, excluding the current record where appropriate.
- Do not unintentionally remove the employee role or alter unrelated roles during an ordinary profile update.
- Do not permit unauthorized role escalation or changes to protected account attributes.
- Follow existing application conventions for employee status and account activation.

### Delete Employee

- Implement deletion according to the application's existing deletion strategy.
- Check foreign-key dependencies, related records, and any existing soft-delete conventions.
- Use transactions when multiple database operations must succeed together.
- Prevent unauthorized deletion and accidental removal of protected accounts.
- Do not delete shared roles or permissions when deleting an employee.
- If the application supports soft deletes, follow that behavior rather than introducing permanent deletion.

## 3. Authorization and Security

- Follow existing authentication, middleware, policies, gates, and permission conventions.
- Protect all employee CRUD routes on the server side.
- Only authorized users may perform employee management operations.
- Prevent unauthorized users from assigning privileged roles.
- Assign the `employee` role automatically during employee creation; do not rely on a user-submitted role value.
- Validate and authorize all requests on the backend.
- Follow existing CSRF protection, mass-assignment protection, and exception-handling patterns.
- Return appropriate validation and authorization errors using the application's established response format.

Do not invent new authorization rules if an established policy or permission structure already exists. Extend the existing structure where required.

## 6. Automated Tests

Inspect existing testing conventions and implement tests for at least the following scenarios:

1. An authorized user can create an employee.
2. An employee is assigned the `employee` role when that role already exists.
3. The `employee` role is created when it does not exist.
4. A newly created employee is actually associated with the role.
5. Repeated employee creation does not create duplicate `employee` roles.
6. Employee creation and role assignment behave correctly when transactional operations fail.
7. Required-field validation works.
8. Invalid email addresses are rejected.
9. Duplicate employee email addresses are rejected where uniqueness is required.
10. Unauthorized users cannot create, view, update, or delete employees.
11. Employee updates preserve existing role assignments unless an explicitly authorized role-management operation is intended.
12. Employee deletion follows the existing deletion and relationship rules.
13. Existing functionality is not broken by the implementation.

Use the existing factories, authentication helpers, permission setup, and test database conventions.

Do not skip or weaken tests to make the suite pass.
